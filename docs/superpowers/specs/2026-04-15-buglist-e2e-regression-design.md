# Buglist 端到端回归收口设计

**日期**：2026-04-15  
**范围**：`buglist.txt` 中 BUG-001～005 的验证收口；ISSUE-006 在有效登录环境下的再确认；文档更新策略。  
**前提**：不在此阶段修改 SDK 业务代码，除非 E2E 稳定复现已标记修复的问题。

## 1. 目标与成功标准

- **目标**：在 **Windows** 与 **WSL（Linux）** 上各执行一次核心端到端用例，确认列表/路径/上传/下载/删除全链路行为与 `buglist.txt` 中已记录修复一致。
- **成功标准**：`TestE2E_Regression_CoreFlow` 在两套环境下均 **完整通过**（含 `DownloadFile` 及内容比对）。
- **失败处理**：单次失败时 **先重跑一次** 以排除网络/OSS 抖动；若稳定失败，在 `buglist.txt` 中更新现象与复现条件，**不**将 ISSUE-006 笼统归为「环境无效」若用户已声明有效登录。

## 2. 执行方式

### 2.1 环境变量与配置

- 启用回归：`E2E_REGRESSION=1` 或 `INTEGRATION_TEST=1`。
- 配置文件：通过 `KUAKE_E2E_CONFIG` 指向含有效 Cookie/访问令牌的 `config.json`；或使用测试在模块/上级目录自动解析的 `config.json`（见 `e2e_regression_test.go`）。

### 2.2 命令

```text
go test ./sdk -run TestE2E_Regression_CoreFlow -count=1 -v
```

在 **Windows（PowerShell）** 与 **WSL** 各执行一次，使用同一有效账号与等价配置（路径按各平台调整）。

### 2.3 平台说明

- **Windows**：验证历史上 `filepath` 与 POSIX 路径混用相关修复（BUG-002～004）在本机是否持续有效。
- **WSL**：提供 Linux 行为下的对照，满足「双平台回归」证据链。

## 3. 文档与变更策略

### 3.1 `buglist.txt`（必做）

新增小节 **「回归验证记录」**，建议字段：

- 日期（UTC 或本地，全文一致即可）
- 平台（Windows / WSL）
- Go 版本（可选）
- 结果（pass / fail）
- 简短备注（失败时附错误类型，如 403/OSS）

对已修复条目（BUG-001～005）：可注明「于下述回归记录中验证」。  
对 **ISSUE-006**：

- 若全流程通过：更新为在有效登录下已于该日期验证通过（或等价表述）。
- 若下载仍失败：更新现象，区分「令牌/会话」与「OSS 回调」等可观察信息，便于后续单独跟进。

### 3.2 `docs/CHANGELOG.md`（可选）

仅当近期 **发版** 或团队 **明确要求** 在变更日志中记录质量门禁时，在下一版本下增加 **一条** 简述；否则可不改，避免无功能变更的条目噪音。

### 3.3 其他文档

仅在 E2E 启用方式或路径说明与现状不一致时，再最小幅度修正 `README.md` 或 `docs/cli.md`；非必选。

## 4. 风险与边界

- **网络与 OSS**：偶发失败不应直接推翻已修复结论；稳定复现才进入代码排查。
- **配置一致性**：Windows 与 WSL 应使用同一逻辑账号；路径仅 `config.json` 位置可不同。
- **范围**：本设计 **不包含** 为 ISSUE-006 实现新的重试/鉴权逻辑；若需代码层修复，应另立变更说明。
